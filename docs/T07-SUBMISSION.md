## 인증 구현 설명서

### ① 무엇으로 붙였나
- 비밀번호 보관: Node 내장 `crypto.scrypt` (N=16384, r=8, p=1, 64바이트). 별도 라이브러리 없음.
- 로그인 유지: 서버가 무작위 32바이트 값을 만들어 HttpOnly·SameSite=Strict(HTTPS에서는 Secure) 쿠키로만 내려줍니다. 서버 DB에는 그 값의 SHA-256 해시만 저장합니다. 만료는 7일입니다.
- 자료 분리: `plans`, `reviews`에 `user_id`를 두고 할 일·실행 기록·완료·태그는 계획을 거쳐 소유자를 따라갑니다.

### ② 왜 그걸 골랐나
비밀번호를 직접 다루는 부분은 널리 쓰이는 해시 방식에 맡기고 직접 만든 암호는 쓰지 않기로 했습니다. scrypt는 Node에 이미 들어 있어 배포 환경(Vercel 서버리스)에서 추가 설치 없이 돌아가고, 메모리를 많이 써서 무차별 대입에 강합니다. 세션은 값 자체를 DB에 두지 않아서, DB가 새어도 그대로는 로그인에 쓸 수 없습니다.

### ③ 어디를 어떻게 고쳤나
- 처음에는 `PRAGMA table_info`로 `user_id` 열이 있는지 보고 없으면 `ALTER TABLE`로 붙였습니다. 로컬에서는 됐지만 Turso 배포에서는 표 만들기가 막혀 서버가 500을 냈습니다. 새 DB는 `user_id`를 처음부터 표 정의에 넣고, 옛 6번 DB일 때만 열이 없는지 조회해서 붙이도록 바꿨습니다. 실패한 SQL 앞부분을 로그에 남기게도 했습니다.
- 그 뒤에도 Turso가 모든 표 생성에 HTTP 400을 돌려줘서, 토큰을 다시 발급해 Vercel 환경변수를 교체하고 재배포하자 해결됐습니다.
- 사용자 에러 문구는 "아이디 또는 비밀번호가 올바르지 않습니다." 하나로 통일했습니다(아이디가 없을 때도 같은 시간의 해시 계산을 합니다).

### ④ 안 열리는 것을 확인한 기록
| 확인 | 결과 | 방법 |
|---|---|---|
| 로그인 없이 `/api/plans` 열기 | 401 "로그인이 필요합니다." | 라이브 주소 직접 열기, 로그아웃 뒤에도 같은 결과 |
| 계정 B의 계획·할 일 목록 | 비어 있음(계정 A 자료 안 보임) | 시크릿 창에서 B로 가입 |
| 남의 계획·할 일 읽기·수정·삭제 | 404로 거절, 반대 방향도 동일 | 자동 테스트 89개 |
| 로그아웃 뒤 옛 세션 / 비밀번호 변경 뒤 옛 세션 | 거절 | 자동 테스트 |
| 계정 삭제 | 계정·계획·할 일·기록 함께 삭제, 다른 계정 자료는 남음 | 자동 테스트 + 라이브에서 B 삭제 |
| 같은 비밀번호 두 계정 | 저장 해시가 서로 다름 | 자동 테스트 |

성공한 요청: 가입·로그인·로그아웃·비밀번호 변경·계정 삭제 / 거절된 요청: 위 표의 401·404·409·429.

### ⑥ 아직 못 막은 것
- 로그인 실패 횟수 제한은 서버 한 대의 메모리 안에서만 동작합니다. 서버리스가 여러 대로 늘면 완전한 제한이 아닙니다. 위험: 느린 무차별 대입을 완전히 막지 못함.
- 두 번째 인증 수단(2단계 인증, 소셜 로그인)은 붙이지 않았습니다. 비밀번호 하나가 뚫리면 계정이 열립니다.
- 비밀번호 재설정과 이메일 확인이 없습니다. 비밀번호를 잊으면 자료를 되찾을 수 없습니다.
- 세션 쿠키를 가진 사람은 7일 안에는 본인처럼 보입니다(기기 분실·화면 공유 주의). 로그아웃이나 비밀번호 변경으로 폐기됩니다.
- 6번에서 로그인 없이 쌓은 옛 자료가 있는 DB에 연결하면, 가장 먼저 가입한 계정이 그 자료를 가져갑니다. 7번 DB는 새로 만들어서 해당 없음.
- 계정 삭제 뒤에도 호스팅 업체(Turso)의 백업에 일정 기간 남을 수 있습니다.
